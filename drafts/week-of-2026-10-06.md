## pull request previews

if your site's source lives on tangled, every pull request can now get its own live copy of
the site, and a comment on the pull request linking to it. push another round and the same
comment updates, newest preview on top, each row linking the commit it was built from.

setting it up is one click in the dashboard's **cli & ci** tab plus one file in your repo:

```yaml
when:
  - event: ["pull_request"]
    branch: ["main"]

engine: microvm
image: nixos

dependencies:
  - nodejs

steps:
  - name: deploy preview
    command: |
      npm install --global --prefix "$HOME/.local" wispctl@2.1.0
      export PATH="$HOME/.local/bin:$PATH"
      wispctl preview deploy --path ./dist
```

that workflow is the same for every repo and every person. it doesn't name your handle, your
subdomain or a host: `wispctl preview deploy` reads the repo, its owner and the commit from
spindle, and takes the subdomain from a webhook record the dashboard writes into your pds. the
dashboard also stores the app password the workflow deploys with straight onto your spindle as a
secret. wisp checks it once and keeps no copy.

each preview is a normal wisp site in **your own pds**, named `pr-<sha7>`, served at
`pr-<sha7>-<you>.preview.wisp.place`. the `<you>` is a wisp subdomain you claimed, and it's there
on purpose: without it, anyone could put a site called `pr-1a2b3c4` in their own repo and answer
for someone else's commit.

the comment comes from a small bot, and the bot trusts nothing it's told. before it writes a
single comment it checks every link in the chain against whoever is actually in charge of it:
your repo record on your pds, the pipeline on the repo's spindle, the pull request record on
its author's pds, the subdomain claim in our database, and finally that the preview url really
serves. if any of those disagree, no comment. this is what keeps the bot from being talked into
posting a phishing link on someone else's pull request.

some honest caveats:

- previews are separate origins, but not a separate registrable domain. cookies scoped to
  `.wisp.place` can reach them.
- pull requests from forks build but don't deploy, because spindle (correctly) never hands
  secrets to code from a fork.
- previews pile up, one per round. `wispctl site prune --prefix pr- --older-than 7` cleans them
  up, and it refuses any other prefix, so it can't eat your real site. the dashboard hides them
  from your site list now too.
- collaborators can turn previews on for repos they work on, deploying into their own pds under
  their own subdomain.

the docs have the full guide: https://docs.wisp.place/guides/preview-deploys/

## wispctl 2.0: the cli, rewritten in rust

wispctl used to be a typescript program that needed bun or node to run. 2.0 is a rewrite in
rust, built on (my fork of) jacquard, and the typescript cli is gone.

why bother:

- **it's one static binary.** the linux builds are fully static, so they run anywhere: nixos,
  alpine, busybox, a ci runner with nothing on it. macos and windows builds too, and nothing
  downloads at install time.
- **it behaves the same.** same commands, same flags, same output in scripts. if you had a
  workflow calling wispctl 1.x, it keeps working.

you can get it however you like:

```sh
npm install -g wispctl            # node shim + the native binary for your platform
npm create wisp@latest            # scaffold a new project
cargo install --locked --git https://tangled.org/nekomimi.pet/wisp.place-monorepo wispctl
```

or grab a binary directly from https://sites.wisp.place/nekomimi.pet/wisp-cli-binaries
(checksums are on that page, the cli docs and the dashboard).

new this week:

- `wispctl preview enable / disable / deploy` for pull request previews
- `wispctl deploy --header "Name: value"` to set response headers at deploy time
- `wispctl site prune` and `wispctl site delete --records`
- `wispctl deploy --preview-host` checks a preview's name before uploading and prints its url

we went 2.0.0 → 2.0.1 → 2.0.3 → 2.1.0 over the week, so if you installed it on day one,
update.

## sign-up, and pds.wisp.place

until now you needed an atproto account somewhere else before you could use wisp. bluesky's is
fine, but a lot of people arriving at wisp don't want a social media account just to host a
website.

so wisp has its own pds now: **pds.wisp.place**, with handles under **fae.mom**. it runs
[tranquil](https://tangled.org/tranquil.farm/tranquil-pds), with a few changes in
[my fork](https://tangled.org/okami.mom/tranquil-pds):

- one simple sign-up form in wisp's colors, instead of the multi-step flow
- **sign in with github**, which goes straight to github without an extra page. github
  sign-ups also get a password, so you're not locked to github forever
- a cloudflare turnstile check on sign-up, because open sign-ups attract bots
- a fix so migrating an existing account onto the pds logs in by your did rather than email
- a link to the exact source of the running build on every page, because tranquil is agpl and
  you should be able to see what you're running on

on wisp's side, the landing page has a sign-in dialog now. if you have an account, sign in; if
you don't, it sends you to pds.wisp.place to make one, and then straight back.

it's a real pds, so the account is yours: you can use it with any atproto app, and you can move
it to another pds whenever you want. it's backed up nightly. **TODO: say whatever you want about

## content-addressed storage

this one you shouldn't notice at all, which is the point.

wisp used to store every site's files under that site: `{did}/{site}/{path}`. two sites with the
same `style.css` stored it twice, and redeploying a site meant fetching every file from your pds
again even if nothing changed. that was fine when people deployed a site now and then. it is not
fine when every pull request round deploys a whole new site.

now a file's contents are stored once, under a name made from its content:
`cas/{cid}.{variant}.{ext}`. the cid is the blob's own content hash from your pds, the variant
covers the things that change the stored bytes (mime type, gzip, base64), and the extension
keeps our caching rules working. each site is just a map from its paths to those names.

what that buys:

- **redeploys and previews are cheap.** a preview round that changes three files fetches and
  stores three files. everything else is already there.
- **files never change once written.** a name contains the content's hash, so updating a site
  never has to invalidate a stored file, only the site's map.
- **cleanup is safe.** a file is only deleted when no site points at it and it has been
  unreferenced for a grace period (a day by default, never under an hour), and a daily check
  recounts references against the actual site maps.

moving every existing site over happened live, while people kept deploying. the migrator had to
cope with sites being updated underneath it, so it checks each site's record hasn't changed
before switching it, and leaves it for the next pass if it has.
